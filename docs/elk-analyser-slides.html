Under the Hood

4-Stage Pipeline

Stage 1Extractor從 Elasticsearch 撈日誌，並管理 Checkpoint（斷點）
Stage 2Preprocessor按 TraceID 分組，建出事件鏈（沒有 TraceID 就用 5 分鐘時間窗口）
Stage 3Bob Bridge呼叫 Bob CLI（log-analyst mode）推理根因
Stage 4Report Builder生成 PPTX 診斷報告，寫入任務紀錄

每個階段只做一件事。分析失敗只影響當次任務，不會更新 Checkpoint。

Why It Works This Way

Key Design Decisions

01

同步 vs 非同步

兩個端點：/analyse 等結果，/analyse/async 先拿 job_id。觸發可靠性的保障。

02

斷點設計

記錄上次結束時間，下次從這裡接續，不漏不重。事件鏈完整性的保障。

03

無異常設計

analyse() 與 build_report() 回傳錯誤 dict 而非丟例外，失敗只影響當次任務。分析冪等性的保障。

04

欄位映射可配置

ES 欄位名稱走 config.yaml，換環境不改程式碼。推理準確性的保障。

Decision 01 — Trigger Reliability

同步 vs 非同步

問題 分析耗時不定 Bob CLI 推理一次可能需要 30–90 秒。告警系統（Grafana Webhook）發出 HTTP 請求後不能一直等，否則連線逾時就失去這次觸發。
設計 兩個端點 /analyse 同步等待，回傳完整結果；/analyse/async 立即回傳 job_id，讓呼叫方稍後輪詢 /jobs/{id}/status。Worker 保持單一佇列，序列執行，避免兩次分析互相干擾。
例子 Grafana 告警 凌晨 3 點資料庫異常，Grafana 觸發 Webhook 呼叫 /analyse。若用同步，30 秒後 Grafana 拿到 200 OK，確認已觸發。若改非同步，Grafana 先拿到 job_id=42，Web UI 隨後顯示「分析中…」直到完成。
Decision 02 — Event Chain Integrity

斷點設計

問題 分析從哪裡開始？ 日誌是連續產生的，每次告警觸發若都從「過去一小時」抓，同一筆錯誤可能被重複分析；若只抓「最新」又可能漏掉剛發生的事件。
設計 記錄游標，接續分析 每次分析成功完成後，把查詢視窗的結束時間存進 Checkpoint（SQLite id=1）。下一次分析從這個時間點繼續，確保不漏不重。失敗的分析不更新 Checkpoint，下次仍從同一點重試。
例子 連續兩次告警 08:00 告警分析了 07:00–08:00，成功，Checkpoint 寫入 08:00。08:30 再次告警，自動從 08:00 接續，分析 08:00–08:30，不會重複看 07:30 的那批日誌。
Decision 03 — Analysis Idempotency

無異常設計

問題 一次失敗不該影響全局 根因分析過程中可能因 LLM 輸出格式異常、ES 連線逾時、報告生成失敗等原因中斷。若直接拋出例外，呼叫方不知道該怎麼處理，且 Checkpoint 可能在錯誤狀態下被更新。
設計 回傳 dict，不丟例外 analyse() 與 build_report() 任何失敗都回傳 {"error": "…"} dict。API 層讀到 error key 就標記任務為 failed，Checkpoint 不移動，下次分析可以從同一個視窗重試，不影響歷史紀錄。
例子 Bob CLI 輸出解析失敗 Bob 回傳的 JSON 多了一層 markdown fence，json.loads() 失敗。若丟例外，程式崩潰，Checkpoint 停在上次位置，下次重啟後重跑同樣視窗。現在則是回傳 {"error": "JSON parse error"}，任務標記 failed，Checkpoint 不動，下次仍可重試同一個時間段。
Decision 04 — Cross-Environment Accuracy

欄位映射可配置

問題 各環境 ES 欄位名不同 Logstash pipeline、不同版本的 APM agent、或客戶自訂 index template，都可能讓同一概念（如「log level」）對應到不同欄位：log.level、severity、level。若寫死在程式裡，換環境就要改程式碼，風險高。
設計 一份 config 對應一個環境 config.yaml 的 field_mapping 區塊宣告欄位別名。Preprocessor 的 _normalise_event() 透過 _safe_get(doc, fm["level"]) 讀值，支援巢狀路徑（如 log.level）。換環境只改 config，程式碼不動。
例子 新環境 onboarding 現有環境用 log.level，新接入的系統用 severity_text。只需在 config.yaml 把 level: "severity_text" 改掉，不需要改 Preprocessor、Bob Bridge 或報告生成的任何程式碼。Bob 收到的 event_chain 格式始終一致。
Why Log Alone Is Not Enough

Log 不知道 Application Flow

Log描述事件告訴你「什麼時間發生了什麼 ERROR」，但不知道服務之間怎麼呼叫、誰先誰後。
APM Trace描述因果鏈告訴你「A 呼叫 B → B 呼叫 C → C 失敗」，以及哪個服務的整體 error rate 最高。
Infra Metrics描述系統狀態告訴你「JVM heap / Artemis queue 在哪個時間點惡化」，量化嚴重程度。

三種信號各有盲點。讓 Bob 有效推理的前提：把三層證據疊加後再傳入。

Design Principles for Effective RCA

讓 Bob 聚焦根因的三個原則

原則 01 Trace ID 是因果主鍵 同一次請求在 Liberty → Artemis → PostgreSQL 產生的 ERROR，用 TraceID 串成單一 event_chain，Bob 看到的是「一次失敗的完整時序」，而非散落的 ERROR。
原則 02 APM 補因果方向 Instana trace_summary 注入各服務的 error rate（如 bankdb 87% vs liberty 3%），讓 Bob 能區分根因與 cascade failure，而非猜測。
原則 03 聚合統計補樣本盲點 es_agg_summary 注入全量錯誤分布，Bob 看到的是「真實比例」，而非從有限樣本重新推斷——直接消除樣本偏差。

無 TraceID 時退守 5 分鐘時間窗口（Fallback），chain_id 前綴為 time_window_，Bob 推理時可識別信心度差異。

Hands-on

Up and Running in 3 Commands

# 1. 啟動服務
podman-compose up --build -d

# 2. 指定時間範圍，觸發一次分析
podman exec elk-analyser python cli.py run \
  --from "2026-01-15 08:00" --to "2026-01-15 12:00"

# 3. 下載 PPTX 報告
curl -o report.pptx http://localhost:8080/jobs/1/report
