候選 #1

資料存取層（DAL）深化

analysis_pipeline.py · api.py · cli.py · extractor.py

Strong
問題

SQL 查詢散落 20+ 處，分佈在 analysis_pipeline、api、cli、extractor 四個模組。每個模組都直接呼叫 sqlite3.connect()，沒有介面隔離。每次請求開啟新連線。

刪除測試：若刪掉所有散落的 sqlite3 呼叫，複雜度會在 20+ 個呼叫端重新出現——這是真實的 seam。

解法

建立一個 深模組 JobRepository：介面只暴露業務操作（create_job、complete_job、fail_job、list_jobs、get_checkpoint、set_checkpoint），所有 SQL 與連線管理藏在實作內。同時增加一個 InMemoryJobRepository adapter，讓測試完全不依賴磁碟。

效益

局部性（Locality）：SQL schema 變動只改一個地方。

槓桿（Leverage）：20+ 個呼叫端免費升級（例如加索引、加重試）。

測試：整個 pipeline 可用 in-memory adapter 跑，無需真實 DB 檔案。

現有問題：api.py:370 的動態 SQL 字串拼接有 SQL injection 風險，集中後可一次修復。

Config 爆炸——參數傳遞鏈深化

全部 7 個模組（每個都有 config_path 預設值）

Strong
問題

config_path: str = "/app/config/config.yaml" 出現在 7 個函式簽名中，並在每次呼叫時重新讀取 YAML。

api.py 在同一個請求內三次呼叫 _load_config()（Lines 57, 123, 149）。每個模組都有獨立的 _load_config() helper——7 個幾乎相同的私有函式。

這是最大的介面噪音：caller 必須知道 config 路徑才能呼叫任何業務函式。

解法

建立 AppConfig——一個 深模組，在 process 啟動時讀一次 YAML，之後透過 module-level singleton 或依賴注入取用。

所有業務函式的 config_path 參數消失，介面收縮。

AppConfig 支援 ELK_CONFIG 環境變數覆蓋，無需重建 container。

效益

槓桿：7 個呼叫端的簽名同時縮短。

局部性：config 讀取邏輯集中一處，含 fallback、validation、型別轉換。

測試：測試時直接建立 AppConfig 物件注入，不依賴磁碟 YAML。

效能：消除每次請求重讀 YAML 的 I/O。

Bob Bridge 輸出解析脆弱性

analyser/bob_bridge.py

Worth exploring
問題

_parse_bob_output() 使用 re.search(r'\{.*\}', stdout, re.DOTALL) 搜尋第一個 JSON 物件，再用字串操作剝除 markdown fence。

這個解析邏輯與 Bob CLI 的輸出格式強耦合——一旦 Bob 更新格式（多了換行、多了包裝 key）就靜默失敗，回傳 {"error": "...", "raw": stdout}。

此外 subprocess 繼承整個 os.environ（Line 97），洩漏父程序所有環境變數。

解法

在 Bob Bridge 內建立一個深化的解析 seam：BobOutputParser 封裝所有解析策略（直接 JSON、markdown fence 包裝、last_message 提取），對外暴露單一 parse(stdout: str) -> dict 介面。

subprocess env 改為白名單傳遞（只傳 BOB_API_KEY、HOME、PATH），不繼承整個 os.environ。

效益

局部性：Bob 輸出格式變動只改一處。

測試：可直接用各種 Bob stdout fixture 測試 parser，不需要跑實際 subprocess。

安全：縮小子程序環境變數暴露面。

注意：ADR-0001 確認 subprocess 模式是刻意設計，本候選不改呼叫方式，只改解析與 env 傳遞。

BEFORE — 脆弱的 inline 解析
def _parse_bob_output(stdout: str) -> dict:
    # 嘗試 1：直接 json.loads
    try:
        data = json.loads(stdout)
        last = data.get("messages", [])[-1]
        content = last.get("content", "")
    except:
        content = stdout

    # 嘗試 2：regex 找 {...}
    m = re.search(r'\{.*\}', content, re.DOTALL)
    if m:
        raw = m.group(0)
        # 嘗試 3：strip markdown fence
        raw = re.sub(r'^```json\s*', '', raw)
        raw = re.sub(r'\s*```$', '', raw)
        return json.loads(raw)
    
    return {"error": "parse_failed", "raw": stdout[:2000]}

class BobOutputParser:
    """唯一的解析 seam，可獨立測試。"""
    
    STRATEGIES = [
        _try_direct_json,
        _try_last_message_json,
        _try_markdown_fence_json,
        _try_regex_json,
    ]
    
    def parse(self, stdout: str) -> dict:
        for strategy in self.STRATEGIES:
            result = strategy(stdout)
            if result is not None:
                return result
        return {"error": "parse_failed", "raw": stdout[:2000]}

run_analysis() 淺層編排器——DB 操作外滲

analysis_pipeline.py

Worth exploring
問題

run_analysis() 的 98 行函式體中，有 6 處直接 sqlite3 呼叫，混在業務流程的 try/except 裡。

_create_job() 函式定義了但函式體內又重複寫了 job 建立邏輯（Line 106-116 vs 函式定義）。

_update_job() 以 WHERE rowid = last DESC LIMIT 1 更新「最新的一筆」，而非以 job_id 更新——這是隱性的競態條件（concurrent jobs 時會更新錯誤的 job）。

解法

從 _create_job() 回傳 job_id（移除 SELECT last_insert_rowid() 反模式）。

所有 DB 操作移入 JobRepository（候選 #1 的結果）。

run_analysis() 變成純業務編排：接受 repo adapter，呼叫 extract/preprocess/analyse/build_report，以 job_id 更新狀態。

整個函式可在沒有真實 DB 的情況下測試。

效益

正確性：消除以 rowid DESC 定位最新 job 的競態條件。

局部性：DB 邏輯不再散落在業務流程中。

測試：pipeline 的整合測試只需 mock 四個 stage 函式和一個 repo adapter，不需要真實 ES 或 Bob。

    conn.commit()

    events = preprocess(...)
    analysis = analyse(...)
    
    # 更新 job（競態！）
    conn.execute("UPDATE analysis_jobs SET ... WHERE rowid = (SELECT rowid ... ORDER BY rowid DESC LIMIT 1)")

AFTER — 純業務編排器
def run_analysis(
    query_from, query_to,
    trigger_mode="on_demand",
    config: AppConfig = None,
    repo: JobRepository = None,   # ← 注入 adapter
):
    config = config or AppConfig.load()
    repo = repo or JobRepository(config.db_path)
    
    job_id = repo.create_job(trigger_mode, query_from, query_to)
    
    try:
        logs = extract(query_from, query_to, config)
        events = preprocess(logs, job_id, query_from, query_to, config)
        analysis = analyse(events, job_id, config)
        report = build_report(analysis, job_id, query_from, query_to, config)
        repo.complete_job(job_id, analysis, report)  # ← 明確 job_id
        repo.set_checkpoint(query_to)
    except Exception as e:
        repo.fail_job(job_id, str(e))
    
    return repo.get_job(job_id)
候選 #5

Preprocessor 使用 id() 追蹤物件識別——脆弱的分群邏輯

analyser/preprocessor.py · Line 159

Worth exploring
問題

preprocess() 先以 trace_id 分群，再對「未被 trace 涵蓋的事件」以時間視窗分群。

識別「已被 trace 涵蓋」使用 id(ev)（Python 物件記憶體位址）建立 seen_ids: set。

這在 CPython 下可行，但物件 id 可能被重用（若舊物件被 GC 而新物件分配在同一位址），且在其他 Python 實作（PyPy）下行為不同。這不是一個可測試的 seam——你不能從介面外部觀察到它用了 id()，但它確實是一個隱藏的錯誤點。

解法

改用 event 的業務識別欄位標記（如 _grouped: bool，或建立一個 set of event index / 業務 id）。

事件分群邏輯本身是純函式（無 I/O），已是一個好的 seam——只需修復識別方式，使其基於業務欄位而非記憶體位址。

效益

正確性：消除潛在的物件 id 重用問題。

可移植性：不依賴 CPython 記憶體模型。

代價小：這是最小的改動，3-5 行程式碼。
